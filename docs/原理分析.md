# 原理分析：为什么 Unity 注册页恒报「验证码无效，请重试」

> 本文记录一次完整的故障定位过程。所有结论都对应可复现的 CDP（Chrome DevTools Protocol）观测，
> 包含被证伪的假设与反证实验，方便他人复核。

---

## 1. 现象

在 `https://login.unity.com/zh/sign-up` 填写：

| 字段 | 内容 |
|---|---|
| 电子邮件 | 任意未注册邮箱 |
| 全名 | 任意 |
| 密码 | 满足「至少 8 位，含字母、数字和符号」 |

点击「创建帐户」后约 4 秒，表单下方出现：

```
验证码无效，请重试
```

**换邮箱、换密码、强刷、换网络、换浏览器** 结果都一样。

---

## 2. 先排除「用户输入有误」

- 密码规则提示是 `至少 8 个字符，包括字母、数字和符号`，输入满足时按钮正常可点，无前端校验报错；
- 换成另一个邮箱（含从未注册过的地址）同样报错；
- 报错文案指向验证码而非账号信息 —— 说明失败发生在人机校验环节，而不是账号唯一性或密码策略环节。

**结论：排除输入问题。**

---

## 3. 抓请求：提交确实发生了，只是缺 token

用 CDP 监听 `Network` 域观察一次提交：

- 提交通过 Next.js 的 **server action** 完成，`POST https://login.unity.com/zh/sign-up`；
- HTTP 状态 **200**，响应是 RSC（React Server Components）文本流；
- 错误信息在响应体里，而不是通过 4xx 状态码表达 —— 所以「看状态码调试」会得出错误结论（以为提交成功了）。

同时在页面里检查验证码对象：

```js
window.grecaptcha                     // 存在
Object.keys(window.grecaptcha)        // ['enterprise', 'getPageId']
window.grecaptcha.enterprise.execute  // undefined   ← 关键
```

**reCAPTCHA 的 SDK 对象存在，但真正能签发 token 的 `execute` 方法没有挂上。**
这意味着脚本「加载了一部分」，但没有完成初始化。

---

## 4. 找到加载链

控制台与 `Network` 显示脚本分两段加载：

1. **加载器**（白名单允许，正常返回 200）

   ```
   https://www.recaptcha.net/recaptcha/enterprise.js?onload=recaptchaEnterpriseOnLoad&render=explicit
   ```

2. **这个加载器返回的桩代码**（stub）并不包含实现，而是动态插入 `<script>`，把真正 payload 指向：

   ```js
   po.src = 'https://www.gstatic.cn/recaptcha/releases/NhfdZHzre166o-vFZrWsq3yu/recaptcha__zh_cn.js'
   ```

   注意两点：
   - 域名是 **`www.gstatic.cn`**（中国区 CDN），不是 `www.gstatic.com`；
   - 语言只影响**文件名**（`recaptcha__en.js` / `recaptcha__zh_cn.js`），域名不变。

3. 这个请求在浏览器里**直接失败**，且 CDP 给出：

   ```
   blockedReason: "csp"
   ```

   —— 请求**根本没有发出去**，是浏览器按策略自己拦的。

---

## 5. 读响应头：CSP 白名单缺一条

`login.unity.com` 的**文档响应头**（不是 `<meta>`）里：

```
content-security-policy: script-src 'self' 'unsafe-eval' 'unsafe-inline'
  https://cdn.cookielaw.org/ https://*.unity.com/ https://www.recaptcha.net/recaptcha/
  https://*.googletagmanager.com/ https://www.gstatic.com/recaptcha/
  https://www.clarity.ms https://plausible.it.unity3d.com/ https://scripts.clarity.ms/
  https://cdn.amplitude.com/; ...
```

`script-src` 里允许了 `www.recaptcha.net/recaptcha/` 和 `www.gstatic.com/recaptcha/`，
**唯独没有 `https://www.gstatic.cn/recaptcha/`**。`frame-src`、`connect-src` 同样没有。

控制台原文：

```
Loading the script 'https://www.gstatic.cn/recaptcha/releases/NhfdZHzre166o-vFZrWsq3yu/recaptcha__zh_cn.js'
violates the following Content Security Policy directive: "script-src 'self' 'unsafe-eval' 'unsafe-inline'
https://cdn.cookielaw.org/ https://*.unity.com/ https://www.recaptcha.net/recaptcha/
https://*.googletagmanager.com/ https://www.gstatic.com/recaptcha/ ..."
```

于是：桩代码 → 插入 script → 被拦 → 初始化中断 → `execute` 不存在 → 无 token → 服务端回「验证码无效」。

---

## 6. 反证实验（决定性）

只做一件事：**临时放行该页的 CSP**（`Page.setBypassCSP({ enabled: true })`），其余不变，然后重跑同一条流程：

| 检查项 | 放行前 | 放行后 |
|---|---|---|
| `www.gstatic.cn/.../recaptcha__zh_cn.js` | `blockedReason: "csp"` | **200** |
| `recaptcha/enterprise/anchor`（site key `6LcRo8YtAAAAAB3koCIH7XljKyZC2lEw_gKH1dPg`） | 未发出 | **200** |
| `recaptcha/enterprise/bframe` | 未发出 | **200** |
| `grecaptcha.enterprise.execute` | `undefined` | **function** |
| 「验证码无效，请重试」 | 出现 | **不再出现** |

单变量改变、结果翻转 —— **CSP 白名单是唯一开关**，此外无需改动任何东西。

---

## 7. 被排除的其他假设

| 假设 | 检验方式 | 结论 |
|---|---|---|
| 邮箱已被注册 | 换成从未使用过的地址 | 无效，文案与账号无关 |
| 密码不满足规则 | 满足全部字符要求 | 无效 |
| 需要重试 / 服务端抖动 | 连续多次、间隔重试 | 稳定复现，非抖动 |
| 被墙（gstatic.cn 连不上） | CDP 看 `blockedReason` 与 DNS | 请求未发出，`csp` 阶段即被拒；DNS 正常解析到国内 IP |
| 换英文页面可绕过 | 访问 `/en/sign-up` | 无效：改用 `recaptcha__en.js`，域名仍是 `www.gstatic.cn` |
| 换浏览器可绕过 | Chrome / Edge / 无扩展干净 profile | 无效：CSP 由页面下发，任何 Chromium 浏览器一致 |
| 是本机网络或代理导致 | 干净 profile、无代理 | 无效，问题可稳定复现 |

---

## 8. 根因与修复建议

**根因**：`login.unity.com` 的 CSP `script-src`（以及 `frame-src` / `connect-src`）白名单遗漏了中国区 CDN 域名
`https://www.gstatic.cn/recaptcha/`，而 reCAPTCHA Enterprise 的加载器在部分网络环境下会把 payload 指向该域名。

**对 Unity 的建议**（任一即可）：

1. 在 `script-src`、`frame-src`、`connect-src` 中补上 `https://www.gstatic.cn/recaptcha/`；
2. 或让加载器始终从已白名单的 `https://www.gstatic.com/recaptcha/` 取 payload（不使用 `recaptcha.net` 的区域重定向）；
3. 顺带修正错误文案：把「验证码无效」改成能区分「缺少 token / 校验失败 / 网络问题」的提示，避免把服务端配置问题归咎于用户输入。

**对用户的可选绕行**：

- 用 Google / Apple / SSO 账号注册（不经该验证码）；
- 用本扩展临时移除该站点的 CSP 响应头；
- 向 Unity 提交问题（本文即完整证据包）。

---

## 9. 复现方式

见仓库 [`verify/`](../verify/) 目录：`run.ps1` 起一个带扩展的独立浏览器实例，`verify.mjs` 输出上文表格并断言。
不带扩展运行即为对照组，可直接对照 `blockedReason: "csp"`。

## 10. 后续：2026-10-29 复查，站点已切换策略

5 天后用同一套脚本复测，**问题不再复现**。差别在 CSP 策略本身：

| | 2026-10-24（旧策略） | 2026-10-29（新策略） |
|---|---|---|
| `script-src` | `'self' 'unsafe-eval' 'unsafe-inline'` + 主机白名单 | `'self' 'nonce-<每次不同>' 'strict-dynamic'` + 主机白名单 |
| `www.gstatic.cn/recaptcha/...js` | `blockedReason: "csp"` | **200** |
| `grecaptcha.enterprise.execute` | `undefined` | **function** |
| 控制台违规 | 1 条 | 0 条 |

原因在于 `'strict-dynamic'`：一旦存在 nonce/strict-dynamic，**主机白名单对脚本不再起限制作用**，
由已信任脚本（Next.js 主 bundle，带 nonce）动态插入的 `gstatic.cn` 脚本会被放行。
这恰好等价于第 8 节建议的第 (2) 条修复路径。

两种策略可能同时存在于灰度中（同一 URL 不同时间/不同分桶可能拿到不同策略），
所以本工具保留两种判定：`load`（无需修复）与 `block`（需要修复），并打印命中的策略类型。

**对本项目的含义**：扩展从「长期必需」变成「应急开关 + 回归探针」；
真正沉淀下来的是**定位方法**（CSP → 加载链 → 反证单变量）与**可自动化的判定脚本**。
