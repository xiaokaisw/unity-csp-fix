一、问题：一个被误判为「用户操作失误」的故障

在 Unity 的账号注册页 https://login.unity.com/zh/sign-up 填完表单、点击「创建帐户」， 约 4 秒后必然出现一行提示：验证码无效，请重试。

维度观察结果
触发条件任意邮箱、任意合规密码，稳定复现
提示文案「验证码无效，请重试」——把矛头指向用户没有通过人机校验
网络面板表单提交 POST /zh/sign-up 返回 200，错误只在响应体里
验证码对象window.grecaptcha 存在，但 grecaptcha.enterprise.execute 是 undefined
控制台一条红色 CSP 违规，且指向验证码的脚本地址

注意第一行与第三行的反差：提交在 HTTP 层是「成功」的。只盯着状态码排查，会一路得出错误结论—— 这正是这类故障最容易带偏方向的地方。

控制台原文（决定性证据）

because it violates the following Content Security Policy directive:

  script-src 'self' 'unsafe-eval' 'unsafe-inline'

             https://www.recaptcha.net/recaptcha/ https://*.googletagmanager.com/
             https://www.gstatic.com/recaptcha/ https://www.clarity.ms ...

DevTools 的网络面板给出同一结论的另一种表述：该请求 blockedReason: "csp"， 即请求根本没有发出去，是浏览器在执行安全策略时自己拦下的。

由此一次性排除的假设：邮箱已被注册？密码不合规？需要重试？被墙？ 换语言？换浏览器？——脚本连请求都没发出，网络与账号因素都不成立。

二、根因：CSP 白名单与脚本真实来源不一致

#环节发生了什么
1加载器recaptcha.net/recaptcha/enterprise.js 返回 200，但内容只是一段桩代码
2桩代码真正的 payload 被写死在 www.gstatic.cn/recaptcha/…/recaptcha__zh_cn.js
3CSP 白名单只允许 recaptcha.net 与 gstatic.com，没有 gstatic.cn
4浏览器拒绝请求在发出之前就被拦下：blockedReason: "csp"
5无 tokengrecaptcha.enterprise.execute 未挂载，服务端回「验证码无效，请重试」

两个关键事实

  • 脚本域名不是按语言变的。切到英文页只是把文件名换成 recaptcha__en.js，域名仍然是 www.gstatic.cn——所以「换成英文页面」这条常见建议无效。
  • CSP 是响应头，不是 meta 标签。它由服务端下发，客户端改设置、清缓存、换浏览器都无法绕过。

反证实验：只改一个变量，故障消失

用 CDP 的 Page.setBypassCSP 仅对该页临时放行 CSP，其余条件完全不变，重跑同一条流程：

检查项放行前放行后
gstatic.cn/…/recaptcha__zh_cn.jsblockedReason: csp200
/recaptcha/enterprise/anchor未发出200
/recaptcha/enterprise/bframe未发出200
grecaptcha.enterprise.executeundefinedfunction
「验证码无效，请重试」出现不再出现
单变量改变、现象整体翻转，且无需触碰账号、网络或密码——CSP 白名单是唯一开关。 这一步是「假设」变成「结论」的分界线。

这为什么值得被认真修

验证码的失败文案天然把责任推给用户，用户于是反复重试、换邮箱、清缓存，实际永远不会成功； 而对该站点而言，这是中国区用户注册链路的一道静默断点。问题不在用户，在一条漏写的白名单。

三、方案：把修复压到两条声明式规则

修复不需要注入脚本、不需要读取页面：只在两个 Unity 域上移除 CSP 响应头， 让本来合法的验证码脚本可以被加载。

#匹配范围动作
1||login.unity.com/移除 content-security-policy、content-security-policy-report-only、x-content-security-policy
2||api.unity.com/移除前两个同名响应头

为什么这样写

  • 用 declarativeNetRequest 而不是 webRequest。前者由浏览器在内部执行静态规则，不需要常驻后台进程，也不申请「读取所有请求」的高危权限。
  • 作用域写死两个域。规则不匹配其它任何站点，误伤面为零。
  • 不含任何 JavaScript。没有内容脚本 → 读不到 DOM、读不到用户输入；没有 fetch → 不收集、不上传。

权限边界（可对照 manifest.json 核对）

能力是否具备
修改响应头是（仅上述两个域）
注入内容脚本 / 读取页面否
tabs / webRequest / cookies否
联网 / 数据上报否
加载后的扩展：3 个文件、ID gaedhnafibanikalmlejcbfjinabolmo、开关为启用状态

为什么不直接用现成的改头插件

  • Header Editor / ModHeader 能用，但代价更大：它们通常要求「读取并修改所有站点的请求」权限，为一条规则开放全站读写，对一个只需两周有效的排障场景并不划算。
  • 所以选择自建最小扩展：权限只到两个域、规则只做一件事、源码全文可审计——30 秒就能读完并判断它安全与否。

四、验证：可复现，且能自动判定

验证不靠肉眼截图，而靠脚本。verify/verify.mjs 用 Chrome DevTools Protocol 直接观察 真实网络与控制台，输出判定 load 或 block，并支持 --expect 断言接进 CI。 

# 起一个带扩展的独立浏览器实例（不碰日常配置）
powershell -ExecutionPolicy Bypass -File verify/run.ps1
# 另开终端验证
node verify/verify.mjs --port 9333 --expect load

五、5 天后复查：站点已自我修复

2026-10-29 用同一套脚本复测，问题不再复现。差别落在 CSP 策略本身：

2026-10-24（旧策略）2026-10-29（新策略）
script-src'self' 'unsafe-eval' 'unsafe-inline' + 主机白名单'self' 'nonce-…' 'strict-dynamic' + 主机白名单
gstatic.cn 脚本被 CSP 拦截200
executeundefinedfunction

原因很直接：一旦策略里出现 'strict-dynamic'，主机白名单对脚本不再起限制作用， 由已信任脚本（带 nonce 的 Next.js 主包）动态插入的 gstatic.cn 脚本会被放行。 两种策略在灰度期可能并存，同一 URL 不同时间可能拿到不同的那一份。

所以本项目对自己的定位也随证据调整：它不是「一个长期必需的补丁」， 而是「一套定位方法 + 一个应急开关 + 一个回归探针」。工具保留 load / block 两种判定， 正是为了在策略并存或回退时仍能给出确定答案。

六、价值、可复用性与边界

沉淀下来的三样东西

  • 一条可复用的排障路径：CSP 违规 → 追加载链 → 读响应头 → 单变量反证。它不依赖 Unity，可迁移到任何第三方脚本被拦的站点。
  • 一个最小化修复范式：能用声明式规则解决的，就不写脚本、不要后台、不开大权限。
  • 一个可执行的结论：把「我验证过」变成 --expect load 这条会失败的断言。

必须说清的边界

  • 移除 CSP 等于关掉该页面一层防护；本扩展只覆盖两个域，注册完成后建议停用，不做「常驻安全降级」。
  • 只适用 Chromium 内核；Firefox 的规则行为不同，未做适配。
  • 这是本地绕行，不是对站点的修复；站点换域名或换验证码供应商时，规则需同步更新。
  • 所有结论都限定在被观测的那一刻——包括「问题存在」和「问题已消失」，两者都需要重新验证才算数。

如果要把这套方法交到别人手上

仓库里 verify/ 可独立于扩展使用：任何一次「验证码加载不出来」的怀疑， 都可以先跑一次 verify.mjs 拿到确定答案，再决定要不要写补丁。 这也意味着，即使有朝一日扩展本身不再需要，工具与文档仍然成立。
